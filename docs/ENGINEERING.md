# Production engineering checklist

Brief section 16: every one of the 111 items is accounted for as **BUILD** (implemented here), **PLATFORM** (provided by Vercel or Supabase, configured and documented) or **NOT NEEDED** (with the reason and what would change that). Paths are relative to the repository root. Operational procedures are in [RUNBOOK.md](RUNBOOK.md); design decisions in [DECISIONS.md](DECISIONS.md).

## SLOs, SLIs and error budget

| SLO              | SLI (how it's measured)                                                                                                            | Target          |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------- | --------------- |
| Availability     | UptimeRobot checks of `/` and `/api/health` every 5 minutes: the share of checks that succeed in a calendar month.                 | 99.5% per month |
| Public page load | Vercel Speed Insights, real users: p95 Largest Contentful Paint on public pages over 28 days.                                      | under 2.5 s     |
| Downloads start  | Server timing of `/api/download/*` (Vercel function duration, p95) plus the CDN's first byte, from Speed Insights and Vercel logs. | under 1 s p95   |

**Error budget.** 99.5% leaves 0.5% of a month, about **3 hours 39 minutes** of downtime (or failing health checks). Within budget, features ship normally. When the month's budget is spent, new features pause: the next work is reliability (the incident's action items, monitoring gaps, tests) until a full month passes within budget. A single incident over 1 hour gets a postmortem whatever the budget.

## Observability in one page

- **Logs** (what happened): structured JSON from pino with a request id on every line, viewed in Vercel's log explorer. The request id is also returned in the `x-request-id` header and shown on error pages, so a report from an editor leads straight to the log lines.
- **Metrics** (how much, how fast): Vercel shows request rate, duration and errors per route; Speed Insights shows real readers' page speed; the System screen shows queue depth, failed jobs, email failures and backups; Analytics and Payments show the journal's own numbers.
- **Traces** (where the time went): OpenTelemetry spans for each request, its Supabase calls and each queue job, sent to Sentry (when configured) or Vercel's tracing.
- **Errors**: Sentry groups exceptions with their trace and release; every unhandled server error is also logged with its request id.
- **Alerts** (when someone must act): UptimeRobot (site down), Sentry (error spike), the daily check (failed jobs, backups, certificate expiry) and reconciliation (payment mismatches) email the people in [On-call](RUNBOOK.md#on-call).

## Measurements

Measured on 30 October 2026 against the production build (`next start`) on a 4-core development container, with the local Supabase stack and the sample content (23 articles). Production on Vercel serves cached pages from the CDN, so real latency for readers is lower; these numbers bound the server's own work.

**Latency and throughput** (autocannon, 10 concurrent connections, 10 s each; milliseconds):

| Route                | Requests/s | p50 | p90 | p97.5 | p99 | max |
| -------------------- | ---------- | --- | --- | ----- | --- | --- |
| `/` (home)           | 171        | 48  | 88  | 120   | 143 | 331 |
| `/issues/1/1`        | 224        | 36  | 64  | 84    | 98  | 734 |
| `/articles/…`        | 226        | 33  | 59  | 89    | 106 | 653 |
| `/search?q=language` | 22         | 427 | 545 | 595   | 639 | 664 |
| `/api/health/live`   | 401        | 23  | 32  | 38    | 42  | 69  |
| `/api/health`        | 187        | 50  | 72  | 88    | 103 | 204 |

Sequential, one request at a time: download redirect p50 12 ms, p95 21 ms, p99 83 ms (60 requests); `/api/v1/articles` p50 8 ms, p95 13 ms; a single search 45–65 ms.

**Tail latency.** The maxima (650–730 ms) are the first renders after start-up while caches fill; p99 stays within 4× p50 for cached pages. Search is the slowest page because each query renders uncached results: about 50 ms of CPU each, so 10 concurrent searches on 4 cores queue to ~430 ms. On Vercel each request gets its own instance; if search ever needs to be faster, cache its result fragment per query.

**Query plans** (`scripts/explain.sql`): archive 0.1 ms (index `issues_status_published_idx`); issue contents with authors and categories 0.2 ms (indexes on `articles (issue_id, sort_order)`, `article_authors (article_id, position)`); article by slug 0.04 ms; weighted full-text search 5.6 ms (GIN `search_vector`); 90-day analytics 0.05 ms (`metrics_daily` primary key). With the sample data some small tables use sequential scans, which Postgres prefers below a few hundred rows; re-run the script after the first year.
